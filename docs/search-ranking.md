# 搜索方案评分、去重与排序

本文记录当前搜索方案从路线生成到最终展示的筛选逻辑，供后续维护使用。改动 `src/search.ts` 中的评分、缓存、seed 筛选、方案多样性或最终截取逻辑时，必须同步更新本文对应章节和下方代码位置。

代码位置以函数名为主要索引。括号内行号对应本文编写时的版本，代码变化后可能移动；行号变化时一并更新，函数名仍可用于 IDE 全局搜索。

## 数据流

1. `generateRoutes(req)`（`src/search.ts:82`）生成几何路线：直接进球、单库和双库翻袋、单库和双库解球，以及简单组合球。合法首碰限制来自 `legalFirstIds`。路线生成只提供搜索入口，不代表方案已成功。
2. `twoCushionBounces(from, to, route)`（`:37`）用展开桌面的镜像坐标求指定两库的交点；`generateRoutes` 逐段做球体遮挡检查后才保留双库候选。真实反弹不采用镜像近似，仍由物理模拟确定。
3. `coarseShots(route, options)`（`src/search.ts:207`）为路线生成方向、力度、击点、杆法和抬杆角度的粗搜参数。开启力度无限制时会附加更高力度样本。
4. `search.worker.ts`（`src/search.worker.ts:16`）可选地先将这些样本交给 WebGPU 粗筛。GPU 返回的路线和击球样本仍交由 `searchPlans` 的 CPU 物理引擎验证；GPU 没有替代合法性判定、精搜或最终排序。无合法结果时 Worker 会再跑完整 CPU 搜索。
5. `searchPlans(req, onUpdate, preparedGrids)`（`src/search.ts:248`）逐杆调用内部 `tryShot(route, input)`（`:259`）。每次以 `PhysicsWorld` 模拟完整击球，并检查首碰、目标球进指定袋、球停止和规则合法性。只有 `success(req, outcome)`（`:184`）通过的候选才创建 `Plan`。
6. 合法候选计算复杂度、走位和初始偏好分数，进入候选集；每种杆法的最佳参数种子再做局部细化。候选完成后先做多样性筛选，再对 finalists 做容错扰动试算并重算分数，最终最多展示 8 个方案。

## 成功与复杂度

`success(req, outcome)` 要求目标球进入用户指定的袋、模拟已停止、规则检查无犯规，并且不允许非目标黑八意外进袋或离台。搜索结果的合法性不由评分权重放宽。

`tryShot` 在 `src/search.ts:292-303` 从真实模拟事件计算复杂度：

- 基础路线：直接进球 4、翻袋 32、解球 38、组合球 43。
- 跳球增加 24，扎杆增加 34；抬杆角度、碰库与多余碰球、偏心击点和高力度继续增加复杂度。
- 结果限制在 0–100。这个数值是相对排序指标，不是物理难度概率。

走位分数由 `positionScore(balls, rules, target)`（`src/search.ts:144`）几何评估下一目标球的直线路径、切球角度、距离、遮挡、白球贴库和可选进球路线数。它不会搜索下一杆。对抗模式下若本杆换人，搜索会反向评估对手的走位机会（`tryShot` 中 `:307-309`）。

## 偏好评分

统一入口是 `planScore(plan, sort)`（`src/search.ts:160`），分数越高越优先。合法性筛选始终先于评分。

| 偏好 | 评分 |
| --- | --- |
| 综合推荐 `balanced` | 简单度 36%、走位 36%、容错 28%。简单度为 `100 - complexity`。 |
| 复杂度最低 `simple` | 简单度 72%、走位 13%、容错 15%。 |
| 下一杆优势 `position` | 简单度 14%、走位 73%、容错 13%。 |
| 容错程度 `robust` | 简单度 13%、走位 14%、容错 73%。 |
| 最花哨 `fancy` | 复杂度 40%、影响球数 28%、杆法技术 17%、路线/事件复杂度 15%。 |

`fancy` 的附加项从 `Plan.outcome.events` 计算：碰撞、碰库、落袋或离台涉及的不同球越多，影响球得分越高；多次碰球和碰库会提高事件复杂度；扎杆、跳球、抬杆角度和偏心击点会提高杆法分；组合球、翻袋和解球路线会获得路线分。各子项封顶 100。事件复杂度与路线标签取较高值，避免同一条路线重复叠加奖励。

偏好类型及 UI 选项分别位于 `src/types.ts:37` 和 `src/main.ts:39` 的 `#sort` 下拉框。更改偏好会清掉现有结果，提示重新搜索（`src/main.ts` 中 `#sort.onchange`）。

## 参数缓存与 seed 筛选

`shotKey(shot)`（`src/search.ts:201`）把杆法、角度、力度、击点、抬杆角度和无限力度模式编码为稳定键。内部 `tryShot` 还把 `route.contact` 加入键（`:259-262`），避免不同接触点误用同一次模拟结果。`seen` 缓存参数的 loss，避免相同参数和接触点重复跑物理模拟；命中缓存时不会再次把同一结果加入候选列表。

粗搜时，所有试算（包括未成功方案）都会竞争每种杆法最多 6 个局部细化 seed（`:316-323`）：

- 成功方案的 loss 是负值，按初始偏好分数决定优先级。
- 未成功方案按是否接近目标接触、目标袋，以及是否已停止等信息计算正 loss；这是为了细化“差一点成功”的方案。
- `distinctSeed(a, b)` 要求角度、力度、抬杆角度或击点至少有足够差异，避免 6 个名额被同一参数邻域占满。

seed 的“去重”是精搜预算控制，不等同于最终 Plan 去重。未成功 seed 可以参与局部细化，但不会作为合法方案显示。

## 最终多样性与截取

完成局部细化后，`diverse(a, b)`（`src/search.ts:189`）比较候选方案：不同杆法、抬杆角度相差超过 12°、路线标签不同、白球最终位置相差超过 0.17 米，或任一方向击点差超过 0.45，视为足够不同。否则分高的方案占位，近似重复路线会跳过。

finalists 最多先取 12 个：先强制保留每种已找到杆法的最高分代表，再按分数从高到低补入与已选方案足够不同的候选（`searchPlans` 中 `:343-354`）。这一阶段发生在容错计算前，分数还没有最终 robustness。

随后对每个 finalist 做 12 次参数扰动：角度 4 次、力度 2 次、左右与高低击点各 2 次、抬杆角度 2 次（`:356-376`）。扰动后仍成功的次数比例作为 `robustness`。之后再次调用 `planScore` 得到最终分数。

最终最多返回 8 项（`:376-378`）：按最终分数排列；先确保输出中每种成功杆法有一个代表，再用高分方案填满剩余名额，最后将结果整体按分数降序排列。若某杆法没有合法结果，不会为它制造占位方案。

## 改动时的维护清单

- 修改 `success`：同步更新合法方案筛选说明和规则边界。
- 修改 `complexity`、`positionScore` 或 `planScore`：同步更新对应公式、权重表和测试说明。
- 修改 `shotKey`、`seen`、`distinctSeed`：说明缓存键和每种杆法的 seed 预算变化。
- 修改 `diverse`、finalists 上限、每杆法代表策略或最终 8 项截取：同步更新方案多样性与输出顺序。
- 新增或更名 `SortMode`：同时更新 `src/types.ts`、`src/main.ts` 下拉框、本文评分表和 `tests/search.test.ts` 排序测试。
- 修改 Worker/GPU 预筛：说明 GPU 粗筛和 CPU 精确验证的边界；保持合法性由 CPU 结果确认。

主要回归测试位于 `tests/search.test.ts`：合法搜索与规则检查、双库翻袋/解球路线生成、偏好权重排序、最花哨评分、力度扩展及输出方案复算。可运行 `npm test` 和 `npm run build`。
